## C1. The regulatory claims are out of date: the US no longer requires SBOMs, and the CRA SBOM obligation does not apply until December 2027
- Verdict: conceded
- Evidence: (a) EO 14028, Sec. 4(e), directs NIST to issue *guidance* that "shall include … (vii) providing a purchaser a Software Bill of Materials (SBOM) for each product directly or by publishing it on a public website". No section mandates SBOMs for software sold to the government (https://www.govinfo.gov/content/pkg/FR-2021-05-17/html/2021-10460.htm). Sec. 10(j) does give the definition that Ch2:88 and Ch1:11 quote. (b) EO 14306 of 6 June 2025, "Sustaining Select Efforts to Strengthen the Nation's Cybersecurity and Amending Executive Order 13694 and Executive Order 14144", struck EO 14144 Sec. 2(a)–(b), which held the attestation and artifact requirements (https://www.govinfo.gov/app/details/DCPD-202500669/; ABA summary https://www.americanbar.org/groups/health_law/news/2025/6/trump-signs-executive-order-amending-cybersecurity-requirements/). As far as I can find, EO 14144 never contained an explicit SBOM mandate, so "extended and reinforced these requirements" had no basis even in January 2025. (c) OMB M-26-05, "Adopting a Risk-based Approach to Software and Hardware Security", is dated **23 January 2026**, not February as the critic says. It rescinds M-22-18 and M-23-16. Agencies "choose whether to require their vendors to provide SBOMs" (https://www.whitehouse.gov/wp-content/uploads/2026/01/M-26-05-Adopting-a-Risk-based-Approach-to-Software-and-Hardware-Security.pdf; DWT 10 Feb 2026 https://www.dwt.com/blogs/privacy--security-law-blog/2026/02/omb-changes-course-on-software-security). The quote is confirmed through secondary reproductions of the OJ text, because eur-lex did not render for me. (e) Ch2:20 cites `EO14028` for the EO 14144 sentence, although `EO14144` is in the bib. ## C3. "Standard package managers report [a cycle] as an error" contradicts npm and the thesis's own data: 30 of 90 graphs have cycles
- Verdict: conceded
- Evidence: Recomputed: 30 of 90 SBOMs have `cycles` > 0 and `nonTrivialSccs` > 0 (max 16 cycles, max 5 SCCs). Every SBOM comes from an npm-family lockfile (53 `package-lock.json`, 36 `yarn.lock`, 1 `pnpm-lock.yaml`). These lockfiles installed without error, so the package manager did not reject the cycle. Ch7:75 reports the same 30. Ch2:116 itself says real SBOMs contain cycles. The sentence at :114 is therefore refuted by the thesis's own dataset. ## C4. SPDX is mischaracterised: 45 relationship types, an explicit DEPENDS_ON edge, separate packages/relationships arrays, and SPDX 3.0 is ignored
- Verdict: partly rebutted
- Evidence: Confirmed by script on the SPDX 2.3 JSON schema (`spdx-spec`, branch `support/2.3`, `schemas/spdx-schema.json`): `relationshipType` has exactly **45** values, including `DEPENDS_ON`, `DEPENDENCY_OF` and the build/dev/optional/provided/test/runtime `_DEPENDENCY_OF` variants plus `DEPENDENCY_MANIFEST_OF`. The document's top-level properties include separate `packages` and `relationships` arrays. So "approximately twenty-five", "represented implicitly" and the claimed "key structural advantage … two distinct top-level arrays" are wrong. The rebuttal is limited. "SPDX 2.3 has no native structure for embedding vulnerability data" is defensible: 2.3 can only point to advisories through `externalRefs` of category SECURITY. It has no vulnerability element, and that element first appears in the SPDX 3.0 Security profile. A real but smaller difficulty also remains: SPDX states dependency edges in either direction and in several typed forms, so they have to be normalised before a graph can be built, whereas CycloneDX has one `dependsOn` form. The honest reason for supporting CycloneDX only is scope and the dataset's generator (cdxgen), and Ch8:69 already lists SPDX input as future work.
- Viva defence: SPDX can express the graph. SBOM Lens supports CycloneDX because it has a single, directed dependency construct and because the evaluation's generator emits CycloneDX. The SPDX importer is future work, not impossible.
- Minimal thesis fix:
  - :30 "Its relationship model is broad --- it defines approximately twenty-five relationship types including … --- but the dependency relationship is represented implicitly as one type among many, and SPDX 2.3 has no native structure for embedding vulnerability data. SPDX is widely adopted for licence auditing workflows but does not natively support the graph structure required for the analysis SBOM Lens performs." → "Its relationship model is broad --- SPDX 2.3 defines 45 relationship types including … --- and dependencies are stated with several of them, in either direction (\texttt{DEPENDS\_ON}, \texttt{DEPENDENCY\_OF}, \texttt{DEV\_DEPENDENCY\_OF} and others), so they must be normalised before a dependency graph can be built.   - :36 "CycloneDX provides the most explicit and semantically unambiguous graph representation available in any SBOM format, eliminating the inference step that SPDX dependency reconstruction would require." → "CycloneDX states every dependency in a single directed form, and it is the format produced by the generator used in the evaluation; SPDX input, which requires normalising its relationship types, is left as future work (\autoref{cp:conclusion})."

## D-new1. The hub/leaf contrast at :154 contradicts the thesis's own edge orientation
- Verdict: new problem (low–medium)
- Evidence: :154: "A vulnerability in a hub component has a blast radius far exceeding that of a vulnerability in a leaf node." In the thesis, edges point from consumer to dependency (Ch2:46, :102), and a "leaf" is a component with no dependencies (Ch6:138: "a graph dominated by leaf packages with none"). - Viva defence: the intended contrast is between widely used components and components few others use. The word "leaf" carries the wrong meaning in this orientation.
