# Chapter 5 — Defender

All code references are at `28113e7` (`git show 28113e7:<path>`) unless stated otherwise. Recomputations were run on `sbom-lens-eval/data/results/*.json` and `data/sboms/*.cdx.json` (90 SBOMs).

## C1. The "five-state remediation lifecycle" does not exist: there are three states, and one is REMEDIATED, not RESOLVED
- Verdict: conceded
- Evidence: `git grep -E "RESOLVED|WONT_FIX|FALSE_POSITIVE|REMEDIATED" 28113e7 -- src backend` finds only `REMEDIATED`, in `useVulnerabilities.js:13`, `VulnerabilityTable.js:19,33`, `VulnerabilityForm.js:152`, `VulnerabilityChart.js:23,40`, `sbom-vulnerabilities/index.js:79,104,210` and `dashboard/index.js:68`. `git log -S WONT_FIX --all` and `git log -S FALSE_POSITIVE --all` return nothing, so the five-state design never existed in any commit. The backend does not validate status: `create_vulnerability(body: dict)` and `update_vulnerability(vuln_id, body: dict)` in `backend/routers/vulnerabilities.py:15,26`, plus the blind merge at `vuln_store.py:50`. A client could therefore store any string, but the tool offers only three states.
- Viva defence: the backend leaves the status free, so the lifecycle is a UI convention and could be extended without changing the API. The two triage states are a sensible extension, but they are future work. There is no honest way to defend the current text.
- Minimal thesis fix: in :4, :53 and :189, say "three-state" and list `NOT_STARTED`, `IN_PROGRESS`, `REMEDIATED`. Delete the WONT_FIX and FALSE_POSITIVE sentences, or move them to future work as "triage states such as won't-fix and false-positive". Add one clause saying that the backend stores the status without validating it.

## C2. The timeline is not a server-side, append-only audit trail
- Verdict: conceded
- Evidence: `src/hooks/useVulnerabilities.js:187-201` builds `timelineEntry` with `date: new Date().toISOString()` (client clock) and `user: "Current User"`, then PUTs the whole array `[...(vuln.timeline || []), timelineEntry]` together with a client-side `lastUpdated`. `backend/store/vuln_store.py:50` (`{**self.vulns[vuln_id], **updates, "id": vuln_id}`) replaces any field, including `timeline`, `cveId` and `purl`. Only `lastUpdated` is overwritten by the server (:51). One small point in the thesis's favour: when a POST carries no `timeline` (as with every OSV record, see `vulnerabilityAPI.js:150-159`), the server creates the first entry with a server timestamp and `user: "System"` (`vuln_store.py:40-42`). Every later entry comes from the client. The thesis claim at :184, that the PUT is limited to status/notes/patchAvailable, is also wrong: the UI only ever sends `status`, `lastUpdated` and `timeline`, and the API accepts any field.
- Viva defence: this is a single-user research prototype with no authentication, so integrity guarantees were never in scope. The timeline is append-only by convention, because the only UI path appends. The server-side `lastUpdated` and the server-created first entry are real.
- Minimal thesis fix: :189: "Each status change made through the interface appends an entry (status, client timestamp, note) to the `timeline` list. The server does not enforce this: `PUT` is an unrestricted partial update, so the timeline is a convenience history, not a tamper-proof audit trail." :59: drop "append-only". :184: "partial update of any field; the interface uses it to change `status`".

## C3. Fetching runs only after a successful new upload, not "whenever an SBOM is selected"; the refresh/409 story does not happen
- Verdict: partly rebutted (minor; the core stands)
- Evidence: the critic is right about the trigger. `fetchVulnsForSBOM(` has one call site, `dashboard/index.js:86` (`handleUploaded`). `UploadBatchDialog/index.js:53-58` calls `onUploaded` only when `!result.isDuplicate`, and `backend/routers/sboms.py:31-38` rejects identical content by SHA-256. Selecting an SBOM or refreshing the page never fetches. The part that is overstated is the claim that the 409 path is something the thesis "does not" mention happening. Two real routes reach it:
  1. Deleting an SBOM does not delete its vulnerabilities (`sboms.py:114-121` only invalidates caches). Re-uploading the same SBOM after deleting it therefore re-runs the fetch, and every pair returns 409. This is a literal case of "the same SBOM is loaded a second time".
  2. Different SBOMs that share components. In the evaluation data, 1,267 of the 3,789 distinct (cveId, purl) pairs occur in more than one SBOM. If all 90 were uploaded, the store would reject 4,954 POSTs with 409. So the deduplication and the "409 as no-op" behaviour (:32, :75) are well motivated and heavily used. The thesis just attributes them to the wrong scenario.

  The "page refresh" claim (:173) and "every time an SBOM is selected" (:32, :169, :38) are wrong. The critic's point about staleness also holds: records are fetched once at upload and never refreshed.
- Viva defence: the deduplication design is sound and exercised often, because SBOMs in one library share many components. The wording described an earlier trigger. Fetching once at upload is a deliberate choice: OSV is queried once per SBOM and not on every navigation.
- Minimal thesis fix: :32 and :169: "invoked automatically when an SBOM is added to the library". :173: "Because the store is shared across the library, an SBOM that shares components with one already loaded (or one re-uploaded after deletion) resubmits pairs that already exist; each receives 409 and is ignored." :38: "the fetch runs for every SBOM uploaded, and SBOMs often share components". Add one sentence of limitation: "Vulnerabilities are fetched once, at upload; advisories published later reach an SBOM only if it is uploaded again."

## C4. The impact endpoint returns two scalars for the queried node, not per-node HITS
- Verdict: conceded
- Evidence: `backend/routers/impact.py:70-84`: `hubs.get(node_id, 0.0)`, returned as scalar `hitsHub` and `hitsAuthority`. Per-node scores exist only in `/global-analysis` (:105-111). `Chapters/06-Network-Science.tex:32` describes this correctly ("the two scores of the analysed component").
- Viva defence: per-node scores for the blast radius can be read from `/global-analysis`, which the frontend already fetches for the HITS overlay. Remediation prioritisation over the blast radius is therefore possible in the tool, just not from this endpoint.
- Minimal thesis fix: :217: "...dominated nodes, and the HITS hub and authority scores of the queried node". :225: "The response also includes the `hitsHub` and `hitsAuthority` scores of the analysed component (scores for every node come from `/global-analysis`, \autoref{sec:hits})."

## C5. Blast radius and dominated set are separate toggles, and re-targeting a node updates only one
- Verdict: partly rebutted (minor; the core stands)
- Evidence: what the thesis gets right: both sets do come back in one response (`impact.py:79-86`), so :231 ("same response ... without an additional round-trip") is true. The two overlays can also be shown together, because `activeModes` is a Map and `_rebuildOverlays` → `applyMultipleOverlays` (`sbom-graph/index.js:194-237`) applies several classes at once. A node context-menu item "Analyze Impact" does exist (`GraphVisualizer.js:614`), so the node is chosen from the context menu. The critic is also right: the modes are separate items in the Analysis menu (`index.js:954-1010`, `handleActivateBlastRadius` :561 and `handleActivateDominator` :585), and the frontend calls the endpoint once per mode. Most importantly, `handleAnalyzeImpact` (:502-527) uses `if (blast-radius) ... else if (dominator)`. With both modes on, right-clicking a new node refreshes only the blast radius, and the cyan overlay still shows the previous node's dominated set.
- Viva defence: the backend design (one response, both sets) is what the paragraph is about, and both overlays can be shown at once. The stale-overlay case is a frontend bug, not a design flaw.
- Minimal thesis fix: :195: "the blast-radius and dominator-tree overlays from the Analysis menu, applied to the node chosen with the context menu's *Analyze Impact*". :235: replace "rendered simultaneously ... within the same interaction" with "Both overlays can be active together; the analyst then reads...". Optionally note that switching to a new node refreshes only the blast radius in the evaluated version. Chapter 4 :189 needs the same correction.

## C6. `patchAvailable` was always false for OSV records; the schema differs from HEAD
- Verdict: partly rebutted
- Evidence: the patch part stands for OSV records: `vulnerabilityAPI.js:158` hard-codes `patchAvailable: false`. But the field is not meaningless in the evaluated system. It is an analyst-set checkbox in the manual-entry form (`VulnerabilityForm.js:26,73,159-160`), and the store keeps it (`vuln_store.py:35`). So "boolean indicating whether a patched version is known to exist" is defensible as an analyst-maintained flag. What the thesis must not imply is that OSV fills it in. The drift part (the `summary`/`fixedVersions` fields and the derived `patchAvailable` at HEAD, commit `b0da73b`) is post-thesis by the task's own definition. The thesis describes the evaluated system at `28113e7`, so the schema list is correct for that version and is not an error. The critic's sub-claim that `add()` silently dropped `summary` is correct (`vuln_store.py:29-43` lists fields explicitly).
- Viva defence: "Patch availability is an analyst annotation in the evaluated version. Automatic derivation from OSV `fixed` events was added afterwards."
- Minimal thesis fix: :54: "patchAvailable — boolean set by the analyst when a patched version is known; the OSV fetch initialises it to false." If the author decides to describe HEAD instead, add `summary` and `fixedVersions` and state the derivation. That is a choice of version, not a correction.

## C7. Deduplication merges distinct advisories that share a CVE alias; Chapter 7 counts include 125 such pairs
- Verdict: partly rebutted
- Evidence: I reran the count and confirm it: 8,868 records, 125 duplicate (cveId, purl) pairs within the same SBOM, 8,743 after deduplication. Per-band totals become 462 / 4,039 / 3,539 / 703 (versus 462 / 4,081 / 3,622 / 703), and 0 SBOMs change any component's worst band. All 125 duplicates have different summaries, so each is a distinct advisory and none is the same record twice. Two parts of the objection are wrong or overstated:
  1. The claim that ":77 cannot happen" is wrong. `uniqueOsvIds` deduplicates only within one fetch. The same OSV entry is fetched again for every SBOM that contains the component. 162 distinct OSV-ID-fallback pairs (264 fallback findings) appear in the data, and 38 of them occur in more than one SBOM. So the case :77 describes does happen, though "rare" is inaccurate.
  2. Ch7:20 claims "exactly the lookup and severity derivation the tool uses". That claim concerns lookup and severity, and both are byte-for-byte the tool's code (`pipeline/vulns.mjs` imports `vulnerabilityAPI.js`). Ch7 does not claim to reproduce storage.

  What stands: the 8,868 are OSV (advisory, component) findings and not records the tool would store, and the (cveId, purl) key silently drops a second advisory that shares a CVE alias. Results for RQ2 and RQ3 are unaffected.
- Viva defence: Chapter 7 counts advisory findings as OSV returns them, which is the more faithful measure of exposure. The tool's storage key is coarser by design: one row per CVE per component, which is what an analyst tracks.
- Minimal thesis fix: :77: "...preventing duplicates when the same OSV entry is fetched for several SBOMs. Because the key is the first CVE alias, two distinct advisories sharing that alias are also collapsed into one record; the first is kept." Ch7:51: add "(advisory–component pairs as returned by OSV; 125 of them share a CVE and component with another and would be stored once by `VulnStore`, without changing any component's worst band)".

## C9. Blast radius has two definitions, which inflates reach from about 12 % to 19 %
- Verdict: partly rebutted
- Evidence: I reran the computation and confirm the numbers. Median reach as computed is 0.186 (range 0.095–0.349). Excluding each vulnerable node from its own radius gives 0.118 (0.040–0.288). Vulnerable nodes alone make up a median 0.079 of non-root nodes. However, inside the thesis the definition is consistent. Ch5:219 defines blast radius as including the node (`+ [node_id]`), and Ch3:115 (`tab:log4j-case`) states explicitly that the blast radius includes "`log4j-core` itself". Ch7:61 defines reach as the share of nodes "in the blast radius of at least one vulnerable component", which is that same inclusive set (`analyse.py:129`). The RQ2 quantity at Ch7:59 is defined separately, in words, as "the number of components that depend on them", and `len - 1` implements exactly that (`analyse.py:94`). It is a constant shift, so it has no effect on Kendall τ. The only contradicting source is CONTEXT.md:21, a project glossary that is not part of the thesis. "Inflates" is therefore overstated: the 19 % is what the stated definition gives. What stands: (a) Ch7:132, "as opposed to how many components are themselves vulnerable", is misleading, because the vulnerable components are inside the 19 % (they alone are 8 %). (b) Ch5:219 calls the set "the upstream consumers of B", but the node is not its own consumer. (c) The glossary disagrees with the thesis.
- Viva defence: including the node is a deliberate convention (the vulnerable component is itself exposed), stated in Ch3 and Ch5 and applied consistently in reach.
- Minimal thesis fix: Ch5:219: "the blast radius is the node together with its upstream consumers". Ch7:132: replace the "as opposed to" clause with "it counts the vulnerable components themselves (median 8%) and the components that depend on them (a further 11%)", or report both figures. Align CONTEXT.md:21 with the thesis.

## C10. The OSV batch query ignores pagination; failures are silent
- Verdict: conceded (severity low, as the critic says)
- Evidence: the OSV querybatch documentation (fetched today) confirms pagination via a per-query `next_page_token` above 1,000 results per query or 3,000 per batch. `vulnerabilityAPI.js:93-113` never reads `next_page_token`. A non-OK response or exception returns `[]` (:100-104), and failed detail fetches are dropped (:122-123, :138). The evaluation is unaffected: the largest SBOM has 387 findings, below 3,000. See D-new1 for a related inaccuracy in the thesis text.
- Viva defence: the evaluated SBOMs (at most 1,000 components) stay far below the limits, and fetch errors cannot block the graph view, as designed.
- Minimal thesis fix: one sentence after :26: "The implementation does not follow OSV's pagination tokens (issued above 1,000 vulnerabilities per query or 3,000 per batch), and a failed OSV request yields an empty result indistinguishable from 'no vulnerabilities'; neither limit was reached in the evaluation."

## D-new1. The thesis contradicts itself on error handling, and the code does neither thing it says
- Verdict: new point (a real problem the critic missed; it strengthens C10)
- Evidence: :32 says errors are "caught and logged at the `console.warn` level". :171 says the hook "swallows errors silently". In the code, OSV failures never reach the hook's `catch`: `fetchVulnerabilitiesForSBOM` returns `[]` with no log (`vulnerabilityAPI.js:100-104`). Only backend POST errors other than 409 are thrown (`useVulnerabilities.js:140`), and they reach `console.warn` (`useVulnerabilityFetcher.js:45-47`). Because the `for` loop is inside the `try` (:38-44), one failed POST aborts all remaining records for that SBOM.
- Minimal thesis fix: make :32 and :171 agree: "OSV failures yield an empty result; a backend error while storing records is logged with `console.warn` and stops the remaining records of that SBOM. Neither blocks the graph view."

## D-new2. Vulnerability records are global and not per SBOM, so remediation status is shared across SBOMs
- Verdict: new point (a real problem the critic missed)
- Evidence: records carry no SBOM identifier (`vuln_store.py:29-43`), the key is (cveId, purl) only, and deleting an SBOM leaves its records (`sboms.py:114-121`). Marking a (CVE, component) pair REMEDIATED in one application's context therefore marks it for every SBOM that contains that PURL. In the evaluation data, a third of the distinct pairs (1,267 / 3,789) occur in several SBOMs. :182 mentions the "global view" but not this consequence for the status workflow.
- Minimal thesis fix: one sentence in §5.4.2: "Records are keyed by CVE and component, not by SBOM, so a status applies to every SBOM containing that component, and records outlive the SBOM that produced them."
