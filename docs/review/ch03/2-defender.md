## C1. Sunshine does compute, and show, which components are transitively affected by each vulnerability. This contradicts the description of Sunshine and Gaps 1–2
- Verdict: partly rebutted
- Evidence: the critic's reading of the code is right. In `sunshine.py`, `ChildrenGatherer.get_children` (:1530) recurses over `depends_on`. It records depths (:1544), guards against cycles (:1545), and pushes vulnerabilities up to each parent with `add_transitive_vulnerabilities_to_component` (:1513). The report has a "Vulnerabilities table" with "Directly vulnerable components" and "Transitively vulnerable components" (:388, :398, filled at :2164). The component table also has a "Dependency of" column (direct dependents, :1340, :1699) and a "Transitive vulnerabilities" column (:1701). So Sunshine reports, for each vulnerability, the set of its transitive dependents. That is SBOM Lens's dependents-only reach, as a list. Two parts of the thesis survive. (a) :20 says the relationships are "at most traversed as a tree", and that is exactly what Sunshine does. `get_children` enumerates every root-to-node path with a deep copy of the path (`copy.deepcopy(parents)`), not a visited-set graph search. It stops with an exception when the path count passes `SEGMENTS_THRESHOLD = 100000` (:1528, :1551; deep copy at :1538). (b) Sunshine computes no dominance, articulation, centrality, cores or communities. The sentence that fails is :134, "They do not report which parts of the application depend on it". :18, "no graph algorithm is run over the structure", is also too strong: a recursive descendant search with cycle detection is a graph algorithm, even if it runs path by path.
- Viva defence: Sunshine propagates vulnerabilities up a tree expansion of the SBOM. It lists the affected consumers, but it does not show them on a graph, it duplicates shared components, and it does not scale to large graphs, because it enumerates paths. Nothing it computes goes past reachability. The novelty of Gap 2 lies in the dominated set, in paths and reach drawn on a single deduplicated graph, and in the structural measures. It does not lie in listing transitive dependents.
- Minimal thesis fix: :18: "and no graph algorithm is run over the structure" → "it does propagate vulnerabilities to every component that depends on them, transitively, and lists those components in a table, but it does so by enumerating dependency paths, and it computes nothing beyond that reachability". :20: "None treats them as a graph to be analysed." → "None computes anything over them beyond reachability." :134: "They do not report which parts of the application depend on it, through which paths, or which components could not be reached without it." → "At most they list the components that depend on it (Sunshine). None shows those components and paths on the dependency graph, and none reports which components could not be reached without it."

## C5. Gap 3 ignores existing structural and exploitability prioritisation in open-source tools: grype ranks by a combined risk score, and OSV-Scanner prioritises by dependency depth
- Verdict: partly rebutted
- Evidence: grype: the Anchore page says "By default, Grype sorts vulnerability results by risk score", a "Calculated risk score combining CVSS, EPSS, and other severity metrics", with KEV as an annotation. Every input to that score describes the vulnerability, not the component's position. So the grype half of the item supports Gap 3's actual claim ("describe the vulnerability rather than where the affected component sits"). Only the list of refinements should add KEV. OSV-Scanner: the guided-remediation page confirms "Resolution and analysis of the entire transitive graph", "Prioritising direct dependency upgrades by the total number of transitive vulnerabilities fixed" and "Prioritising vulnerabilities by dependency depth, severity". This is real, if shallow, structural prioritisation. But the same page says "This feature is experimental and might change or be removed", and the supported inputs are manifests and lockfiles (`package-lock.json`, Maven `pom.xml`), not SBOMs. The thesis survey is of SBOM tools. Gap 3's second sentence still holds for OSV-Scanner too: it does not rank components that have no CVE.
- Viva defence: SBOM Lens queries OSV, but not OSV-Scanner. The closest prior structural prioritisation is depth and fix-count in an experimental lockfile remediation mode. SBOM Lens goes beyond depth (centrality, spectral exposure, cores, communities) and also ranks components that have no CVE.
- Minimal thesis fix: :136: "sometimes refined by exploit likelihood (EPSS)" → "sometimes combined with exploit likelihood (EPSS) and known exploitation (CISA KEV) into a risk score, as grype does by default". Add: "Outside SBOM tooling, OSV-Scanner's experimental guided remediation for lockfiles also weighs dependency depth and the number of vulnerabilities an upgrade fixes; position in the graph beyond depth is not used."

## C6. Gap 4 and §3.2.4 claim the single-SBOM graph "has not been systematically analysed". Recent SBOM-graph studies exist, and Garcia et al. 2025 is not used in Ch3
- Verdict: partly rebutted
- Evidence: both arXiv papers exist as described. Zięba-Kozarzewski (2607.22140, 2026-07-24) characterises declared edges in 77,092 SBOMs: 52.9% have no edges, a degenerate regime leaves most components orphaned, and 38.3% form well-connected graphs. Baird and Moin (2601.20158, 2026-01-28) train a heterogeneous graph attention network on enriched SBOM graphs to predict vulnerable components. Neither applies the toolkit Gap 4 names, "these methods" (§3.2.4: degree distributions, clustering, path lengths, centrality, communities, power-law fitting). The first measures connectivity regimes; the second learns a classifier. So the specific claim survives. What does not survive is the absolute wording ("absent from ... the research literature", :130; "has not been systematically analysed", :138), and the omission of two directly relevant SBOM-graph papers. Liu 2022 (C6c) resolves per-package trees, but its findings are about the npm ecosystem as a whole, not one application, so it does not undercut Gap 4. On the threat-to-validity point, the evaluation already handles it: Ch7:40 rejects 24 candidates because the "Root without dependency edges in the generated SBOM", and :39 another 103 with an empty production graph. Ch3 does not cite Garcia 2025; Ch1:29 does.
- Viva defence: the 2026 SBOM-graph studies show that the graph is starting to be studied (its completeness, learned predictors), but none characterises the single-SBOM graph with network-science measures or tests whether ecosystem properties hold at that scale, which is RQ1. The edge-completeness finding is real and is why the evaluation generates its own SBOMs from lockfiles and filters edgeless ones.
- Minimal thesis fix: :130: "four capabilities absent from current tooling and the research literature" → "four capabilities that, to our knowledge, current tooling and the research literature do not provide". :138, after "systematically analysed with these methods": add "Recent work has begun to study SBOMs as graphs --- whether their dependency edges are declared at all \citep{ZiebaKozarzewski2026}, and learned prediction of vulnerable components over enriched SBOM graphs \citep{Baird2026} --- but not with the network-science measures above." §3.1, first paragraph: add "A 2025 landscape study of 84 open-source SBOM tools \citep{Garcia2025} has no category for analysing the dependency structure an SBOM records; the four tools surveyed here are among the most widely used." Optionally, in Ch7's threats to validity, cite the 52.9% figure as the reason for the edge filter.

## C10. "Have established that open-source ecosystems form large, scale-free graphs" is not what the three cited studies show, and it sits two paragraphs before the chapter's own warning (Clauset 2009) about such claims
- Verdict: conceded

## C15. "No analysis of that SBOM ... could have detected the attack" overlooks that the trojanised DLL is a component whose hash would change. The DLL also sits inside Orion's own dependency graph
- Verdict: partly rebutted
- Evidence: CISA AA20-352A: "The adversary added a malicious version of the binary solarwinds.orion.core.businesslayer.dll into the SolarWinds software lifecycle, which was then signed by the legitimate SolarWinds code signing certificate". The critic misreads the second quote. "Platform versions that share the same DLL version number" means that two Orion releases ship one DLL version. It does not say that the trojanised DLL kept the version of a clean one. More importantly, the injection happened during the build, so the shipped release never had a clean SBOM to compare against. A hash in the SBOM of the compromised build would simply be the hash of the trojanised DLL. Detection needs an independent reference build, which is the provenance and build-integrity point the text already makes. So "no analysis of that SBOM could have detected the attack" holds. "Listed the same components before and after the injection" is slightly loose: identities would match, but hashes from two independent builds would not.
- Viva defence: an SBOM hash is only as trustworthy as the build that produced it. Comparing it with a reproducible reference build is a provenance control (SLSA), not SBOM analysis, which is the section's conclusion.
- Minimal thesis fix: :92: "would have listed the same components before and after the injection" → "would have listed the same component names and versions as an uncompromised build; only file hashes, compared against an independent reference build, could have differed". The rest unchanged.
